## 5. 30 秒面试讲法

Bear Code 是我用 Python 实现的一个自进化命令行 Coding Agent。它的核心是自研 Agentic Harness，不是简单套 API，而是统一编排模型推理、工具调用、权限控制、Memory、Skills、MCP 和子 Agent。最大亮点是 Skills 自进化与评测：系统会把用户下一轮反馈作为证据沉淀成 `SKILL.md`，再用真实 replay、规则编译、LLM judge、candidate variants 和 champion 机制评估 Skill 是否稳定可用。

## 6. 1 分钟面试讲法

这个项目主要解决两个问题：第一，怎么把大模型变成能安全执行软件工程任务的本地 Agent；第二，怎么让 Agent 在使用过程中沉淀能力。  

我实现了一个 Python Agentic Harness，负责模型调用、tool call 解析、权限检查、工具执行、结果回写、上下文压缩和会话保存。上层支持文件读写、代码搜索、Shell、Plan Mode、OpenAI / Anthropic 双协议、Memory、Skills、MCP 和子 Agent。  

项目最核心的亮点是自进化 Skills 和在线评测。每轮回复结束后系统会保存 pending window，下一轮用户反馈会被合并为证据，再由 Extractor 抽取可复用候选，Maintainer 判断 add / merge / discard，最后写入或演化 `SKILL.md`。评测阶段会从 provenance 构造 replay，编译规则，调用 LLM judge，结合 usage stats 给出状态；如果历史回复失败，还会生成 candidate variants 重新试跑并记录 champion 产物。整个过程有权限控制、provenance 记录、版本快照和评测产物，不是无约束让模型随便改 prompt。

## 7. 2 分钟深度讲法

Bear Code 的底层是一个自研 Agentic Harness。用户输入进入 `Agent.chat()` 后，系统会初始化 MCP、检索相关 Skills、预取 Memory，然后根据配置选择 OpenAI-compatible 或 Anthropic-compatible 模型接口。模型如果返回 tool call，Harness 会先进入统一的权限检查逻辑，再分发到内置工具、Skill、MCP 工具或子 Agent，执行结果会作为 tool result 回写给模型，形成推理、行动、观察、继续推理的闭环。

我在这个闭环上做了几个扩展：第一是 Plan Mode，复杂任务先只读分析和写计划，审批后再执行；第二是 Memory 和 Skills 分层，Memory 记录事实和偏好，Skills 记录可复用方法；第三是 MCP Client，通过 stdio JSON-RPC 动态接入外部工具；第四是子 Agent，用隔离上下文处理探索、规划和局部任务。

最重要的是 Skills 自进化和在线评测。系统会把用户任务、助手回复和下一轮用户反馈组成 pending window，用 Extractor 抽取未来可复用的规则，再由 Maintainer 基于已有 Skills 做相似检索和 add / merge / discard 判断。新增或演化时会写 `SKILL.md`，记录 usage、provenance、版本快照和 retrieved / relevant / used 统计。随后 `/skill-eval` 会基于在线日志构造 replay 样本池，从 Skill 文本编译规则，使用程序检查和 LLM judge 评估历史回复，并根据失败规则生成 candidate variants 重新试跑；只有证据足够且候选优于当前版本时，才记录 champion 产物，保证自进化能力可控、可追溯、可比较。

## 9. 面试高频问题和回答

### Q1：为什么说它是 Harness Agent，而不是普通聊天机器人？

普通聊天机器人主要是用户输入、模型回复。Bear Code 的核心是 Harness：模型只提出 tool call，真正的文件读写、Shell、Skill、MCP 和子 Agent 都由 Runtime 统一做权限检查、执行调度、结果回写和状态保存。也就是说，它有完整的推理、行动、观察、继续推理闭环。

### Q2：自进化 Skills 到底怎么实现？

每轮回复结束后保存 pending window。下一轮用户输入会作为上一轮反馈证据合并进去，然后进入 `online_ingest()`：Extractor 从对话窗口抽取最多一个可复用候选 Skill；Maintainer 结合已有 Skills 做相似检索，判断 add、merge 或 discard；最后调用 `create_skill_file()` 或 `evolve_skill_file()` 写入 `SKILL.md`，并记录 provenance、usage stats 和版本快照。

### Q2.1：Skills 评测怎么做？

`/skill-eval` 会读取在线 provenance、usage stats 和 active Skills，按 Skill 形成 lineage，并从历史对话构造 replay pool。评测先从 `SKILL.md` 编译规则，包括非空、JSON、表格、引用来源等程序规则，以及 LLM judge 的 `skill_instruction_alignment`。然后系统评估历史 `latest_assistant` 是否满足规则，并结合 retrieved / relevant / used 判断 `unobserved`、`incubating`、`watch` 或 `healthy`。

如果有失败规则，系统会生成 candidate variants：一类是根据失败规则追加约束的 heuristic candidate，另一类是 LLM candidate。候选变体会重新生成 replay 回复，再用同一套规则评测，并记录 `candidate_count`、`best_candidate_score`、outputs、judgments 和 summary。只有候选明显优于 current active，并且样本、规则和 usage gate 都达标时，才可能写入 champion 产物。

### Q3：怎么避免沉淀垃圾 Skill？

有三层控制。第一，Extractor 规则限制只抽取用户明确给出的、未来同类任务可复用的规则，不沉淀一次性内容、隐私、URL、账号 ID、精确日期和临时项目事实。第二，Maintainer 会和已有 Skills 做 exact identity 和相似检索，优先 merge 或 discard，避免重复膨胀。第三，usage tracking 会统计 retrieved、relevant、used，长期被检索但不用的 Skill 可以归档。

评测层还有一层保护：Skill 不会因为被创建就默认健康，必须有 replay 样本、promotion-test 样本、规则通过率和 usage 指标支撑。candidate variants 只写入评测产物，不会自动覆盖 active `SKILL.md`，避免模型把一次失败样本直接改成线上能力。

### Q4：Memory 和 Skills 的区别是什么？

Memory 记事实和偏好，例如用户喜欢先看结论、项目当前目标是什么。Skills 记方法和流程，例如代码审查要先列风险、政府报告要使用正式语体和固定结构。简单说，Memory 解决“知道什么”，Skills 解决“怎么做”。

### Q5：怎么保证 Agent 不乱改文件？

首先有 Plan Mode，大范围任务可以只读探索并写计划。其次工具层有统一 `check_permission()`，危险 Shell、新建文件、Skill 创建/演化会确认。再次，编辑已有文件前必须先 `read_file`，并记录 mtime；如果文件在读取后被外部修改，会要求重新读取。

### Q6：MCP 在项目里起什么作用？

MCP 用来把外部工具接入 Agent。Bear Code 自己实现了 stdio JSON-RPC MCP Client，会读取 `.mcp.json` 或 settings，启动 MCP Server，执行 initialize 和 tools/list，把外部工具包装成 `mcp__server__tool`，模型调用时再路由到对应 server 的 tools/call。

### Q7：为什么要支持子 Agent？

子 Agent 用来隔离上下文和任务范围。比如 explore 只读搜索代码，plan 只读输出方案，general 可以处理局部任务。这样主 Agent 不需要承载所有搜索细节，复杂任务也能拆分成更小的独立上下文。

### Q8：项目最大的技术难点是什么？

难点不是调用模型 API，而是把模型、工具、权限、上下文、长期记忆和自进化沉淀串成稳定闭环。尤其是自进化部分，既要能自动沉淀用户反馈，又不能让模型无约束修改自己的能力，所以需要 pending window、Extractor、Maintainer、权限控制、版本快照和 provenance 审计。
