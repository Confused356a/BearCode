# Bear Code 技术亮点详解

本文档用于说明 Bear Code 的核心技术亮点，并把每个亮点落实到具体代码。它不是简单罗列功能，而是回答三个问题：

- 这个亮点解决了什么工程问题？
- 项目里是怎样实现的？
- 关键代码应该从哪里读？

Bear Code 的整体定位是一个轻量级 Coding Agent Runtime。它把大模型调用、工具系统、权限控制、长期记忆、Skills、自进化、MCP、子 Agent、会话恢复和上下文压缩组织成一个可运行闭环。项目的亮点不在于单个工具多复杂，而在于这些能力之间有清晰的数据流、权限边界和持久化审计。

## 1. 技术亮点总览

| 亮点 | 解决的问题 | 核心文件 | 关键入口 |
|------|------------|----------|----------|
| Agentic Harness | 统一编排模型、工具、上下文和状态 | `agents/agent.py` | `Agent.chat()`、`_execute_tool_call()` |

## 2. 亮点一：Agentic Harness 运行时编排

### 2.1 解决的问题

一个 Coding Agent 不能只是“调用一次模型”。真实的编码任务需要循环：

```text
用户输入
  -> 构建上下文
  -> 调用模型
  -> 模型发起工具调用
  -> 权限检查
  -> 执行工具
  -> 工具结果回写模型
  -> 模型继续推理
  -> 保存会话和后台沉淀
```

Bear Code 的 Agentic Harness 就是这套循环的运行时实现。它的价值是：模型不直接操作本地环境，所有动作都经过 Runtime 统一管理。

### 2.2 核心代码入口

核心入口在 `Agent.chat()`：

```text
agents/agent.py:360
```

关键步骤：

```text
首次 chat 初始化 MCP
  -> 弹出上一轮 pending skill extraction window
  -> 检索 Skills 并注入用户消息
  -> 根据协议选择 _chat_openai 或 _chat_anthropic
  -> 等待模型和工具循环结束
  -> 收集 assistant 文本
  -> 调度 skill usage tracking
  -> 调度 online skill evolution
  -> 保存新的 pending extraction window
  -> 自动保存 session
```

对应代码点：

- `agents/agent.py:360`：首次对话懒加载 MCP。
- `agents/agent.py:376`：弹出上一轮 pending window，把下一轮用户输入作为反馈证据。
- `agents/agent.py:377`：检索并注入 Skills 上下文。
- `agents/agent.py:383`：根据 `self.use_openai` 选择 OpenAI 或 Anthropic 路径。
- `agents/agent.py:395`：调度 Skill usage tracking。
- `agents/agent.py:397`：调度在线 Skill 自进化。
- `agents/agent.py:398`：保存本轮 pending extraction window。
- `agents/agent.py:405`：自动保存会话。

### 2.3 工具调度入口

工具调用统一从 `_execute_tool_call()` 进入：

```text
agents/agent.py:993
```

分发逻辑：

| 工具类型 | 处理方式 |
|----------|----------|
| `enter_plan_mode` / `exit_plan_mode` | 交给 `_execute_plan_mode_tool()` |
| `agent` | 交给 `_execute_agent_tool()` 启动子 Agent |
| `skill` | 交给 `_execute_skill_tool()` |
| `mcp__server__tool` | 交给 `McpManager.call_tool()` |
| 其他内置工具 | 交给 `tools.execute_tool()` |

这说明 `agent.py` 是上层调度器，`tools.py` 是基础工具执行层。这样设计可以避免把子 Agent、Skill fork、MCP 路由等运行时逻辑硬塞进基础工具模块。

### 2.4 工程价值

这个 Harness 的核心价值有四点：

- **控制权集中**：所有动作都从 Runtime 走，不让模型直接操作环境。
- **协议可替换**：OpenAI-compatible 和 Anthropic-compatible 两套后端共用上层状态和工具体系。
- **能力可扩展**：内置工具、MCP 工具、Skill、子 Agent 都能被统一调度。
- **可沉淀**：每轮任务结束后可以自动记录 usage、pending window 和 session。

## 3. 亮点二：双协议模型适配

### 3.1 解决的问题

不同模型服务的工具调用格式不同。Anthropic 和 OpenAI 的消息结构、工具定义、工具结果回写格式都不一样。如果项目只支持一种协议，就很难接入不同供应商或代理服务。

Bear Code 的方案是：CLI 层解析 API 配置，Agent 层维护两套路由，但上层工具、Memory、Skills、权限和会话逻辑尽量复用。

### 3.2 配置判断逻辑

协议判断在 `agents/main.py`：

```text
_resolve_api_config()
```

规则：

- 如果 base URL 路径包含 `/anthropic`，走 Anthropic-compatible。
- 如果配置了 OpenAI API key 或 OpenAI base URL，走 OpenAI-compatible。
- 支持通用 `APIKEY` 和 `API`，便于接入 DeepSeek、代理网关等。

### 3.3 OpenAI 路径

OpenAI-compatible 主循环入口：

```text
agents/agent.py:1453
```

关键点：

- `agents/agent.py:1455`：把用户消息追加到 `_openai_messages`。
- `agents/agent.py:1462`：启动 Memory 预取。
- `agents/agent.py:1471`：每轮模型请求前运行上下文压缩流水线。
- `agents/agent.py:1496`：调用 `_call_openai_stream()`。
- `agents/agent.py:1513`：读取 `tool_calls`。
- 后续会逐个解析 function name 和 arguments，走权限检查与工具执行。

### 3.4 Anthropic 路径

Anthropic-compatible 主循环在 `_chat_anthropic()`。它和 OpenAI 路径的理念一致，但消息结构不同：

- Anthropic 使用 `tool_use` block 表示工具调用。
- 工具结果用 `tool_result` block 回写。
- system prompt 作为 API 参数传入，而不是放在 messages 第一项。

项目在 `agent.py` 内部维护 `_anthropic_messages` 和 `_openai_messages` 两套历史，避免格式互相污染。

### 3.5 工程价值

双协议适配体现的不是“多写一个 if”，而是把后端协议差异限制在 Agent 模型调用层。工具、权限、Skills、Memory、MCP 不需要关心底层模型是哪种协议。

## 4. 亮点三：工具系统与权限控制

### 4.1 解决的问题

模型可以请求读文件、写文件、执行 Shell。如果没有权限控制，风险很高：

- 覆盖用户未提交代码。
- 执行危险命令。
- 在 Plan Mode 下提前修改文件。
- 创建或演化 Skill 时写入错误内容。
- 基于过期文件内容编辑。

Bear Code 把工具定义、权限判断和执行逻辑集中在 `agents/tools.py`。

### 4.2 工具定义

内置工具定义在：

```text
agents/tools.py:43
```

工具 schema 包含：

- `name`
- `description`
- `input_schema`

主要工具：

| 工具 | 说明 |
|------|------|
| `read_file` | 读取文件并带行号返回 |
| `write_file` | 写文件 |
| `edit_file` | 基于精确字符串替换 |
| `list_files` | 按 glob 列文件 |
| `grep_search` | 搜索文件内容 |
| `run_shell` | 执行 Shell |
| `skill` | 调用 Skill |
| `skill_create` | 创建 Skill |
| `skill_evolve` | 演化 Skill |
| `agent` | 启动子 Agent |
| `tool_search` | 激活延迟工具 |

### 4.3 权限分层

权限入口：

```text

```

`check_permission()` 返回三类结果：

```text

```

关键逻辑：

- `agents/tools.py:612`：先检查 settings 中的 allow/deny 规则。
- `agents/tools.py:618`：只读工具直接允许。
- `agents/tools.py:621`：Plan Mode 阻断编辑工具。
- `agents/tools.py:627`：Plan Mode 阻断 Shell。
- `agents/tools.py:633`：`acceptEdits` 自动允许编辑类工具。
- `agents/tools.py:639`：危险 Shell 需要确认。
- `agents/tools.py:642`：写新文件需要确认。
- `agents/tools.py:648`：演化 Skill 需要确认。
- `agents/tools.py:651`：创建 Skill 需要确认。
- `agents/tools.py:656`：`dontAsk` 下自动拒绝需要确认的操作。

### 4.4 编辑前读取保护

工具执行入口：

```text
agents/tools.py:670
```

读前保护逻辑：

- `agents/tools.py:673`：执行 `read_file`。
- `agents/tools.py:675`：读取成功后记录文件绝对路径和 mtime。
- `agents/tools.py:683`：写或编辑已有文件前检查是否读过。
- `agents/tools.py:686`：没读过则拒绝编辑。
- `agents/tools.py:689`：mtime 变化则要求重新读取。

这是一条重要的工程保护线。它不是单纯靠 prompt 要求模型“先读文件”，而是在工具层硬性检查。

### 4.5 技术亮点

工具系统的亮点在于它把“模型意图”和“环境动作”隔开：

```text
模型只产生 tool call
Runtime 判断权限
工具层执行实际动作
结果回写模型
```

这让项目具备清晰的安全边界，也方便扩展新工具。

## 5. 亮点四：Plan Mode 安全工作流

### 5.1 解决的问题

大范围修改时，Agent 如果一开始就写文件，容易在没有理解上下文的情况下做错。Plan Mode 的目标是让 Agent 先只读探索、写计划，再由用户决定是否执行。

### 5.2 核心实现

Plan Mode 有两层约束。

第一层是 system prompt 约束：

```text
agents/agent.py:_build_plan_mode_prompt()
```

进入 Plan Mode 后，system prompt 会要求模型：

- 只读探索。
- 只能使用读文件、列文件、搜索。
- 只能写计划文件。
- 完成计划后调用 `exit_plan_mode`。

第二层是工具权限硬约束：

```text
agents/tools.py:621
```

即使模型没有遵守 prompt，`check_permission()` 也会阻止：

- 编辑工具。
- Shell 命令。
- 非 plan 文件写入。

### 5.3 计划审批流程

Plan Mode 工具执行在：

```text
agents/agent.py:1054
```

关键点：

- `agents/agent.py:1055`：处理 `enter_plan_mode`。
- `agents/agent.py:1058`：保存进入前权限模式。
- `agents/agent.py:1060`：生成计划文件路径。
- `agents/agent.py:1061`：拼接 Plan Mode prompt。
- `agents/agent.py:1066`：处理 `exit_plan_mode`。
- 后续根据用户选择继续规划、清空上下文执行、保留上下文执行或手动执行。

### 5.4 工程价值

Plan Mode 的价值是把 Coding Agent 的风险工作流显式化：

```text
只读理解 -> 结构化计划 -> 用户审批 -> 执行修改
```

这比“直接修改，然后再让用户 review”更适合重构和复杂任务。

## 6. 亮点五：Skills 加载、检索与执行体系

### 6.1 Skills 解决的问题

普通 Agent 的经验停留在当前上下文中。用户每次想要固定风格、固定审查流程或固定领域方法，都要重新提示。

Bear Code 用 Skills 把可复用方法沉淀成磁盘上的 `SKILL.md`，并在后续任务中自动检索、注入或调用。

### 6.2 Skill 的内部表示

Skill 数据结构在：

```text
agents/skills.py:23
```

`SkillDefinition` 包含：

- `name`
- `description`
- `when_to_use`
- `allowed_tools`
- `user_invocable`
- `context`
- `prompt_template`
- `source`
- `skill_dir`

这说明 Skill 不是简单字符串，而是有元信息、执行模式和来源的可管理对象。

### 6.3 Skill 加载机制

加载入口：

```text

```

加载规则：

- `agents/skills.py:87`：先加载用户级 `~/.bear/skills`。
- `agents/skills.py:90`：再加载项目级 `.bear/skills`。
- `agents/skills.py:91`：项目级加载时 `overwrite=False`，避免覆盖同名用户级 Skill。
- `agents/skills.py:103`：文件必须叫 `SKILL.md`。
- `agents/skills.py:114`：解析 frontmatter 和正文。
- `agents/skills.py:123`：`user-invocable` 默认 true。
- `agents/skills.py:124`：`context` 支持 `inline` 和 `fork`。
- `agents/skills.py:126`：解析 `allowed-tools`。

### 6.4 Skill 检索机制

检索入口：

```text
agents/skills.py:255
```

检索策略：

- `agents/skills.py:261`：对用户 query 分词。
- `agents/skills.py:269`：提取 Skill 元数据词。
- `agents/skills.py:270`：提取 Skill 正文词。
- `agents/skills.py:271`：元数据词乘以 3，提高 `name`、`description`、`when_to_use` 权重。
- `agents/skills.py:281`：使用 BM25 风格参数 `k1` 和 `b`。

检索结果格式化在：

```text

```

会生成 `<retrieved_skills>` 块注入用户消息。`Agent._augment_user_message_with_skill_context()` 在 `agents/agent.py:447` 调用它。

### 6.5 Skill 执行机制

执行入口：

```text

```

执行流程：

- 按名称找到 Skill。
- 记录 invocation。
- 替换 `$ARGUMENTS` 或 `${ARGUMENTS}`。
- 替换 `${CLAUDE_SKILL_DIR}`。
- 返回 prompt、工具白名单、执行模式和来源。

Agent 层执行在：

```text
agents/agent.py:1014
```

如果是 `inline`：

```text
返回 Skill prompt 给主模型继续执行
```

如果是 `fork`：

```text
创建子 Agent
  -> 使用 Skill prompt 作为 system prompt
  -> 使用 allowed_tools 限定工具
  -> 独立 run_once
  -> 返回结果给主 Agent
```

对应代码在 `agents/agent.py:1021` 到 `agents/agent.py:1052`。

### 6.6 技术亮点

Skills 体系的技术亮点是把“可复用能力”做成了磁盘文件、可检索对象和可执行工具三者的统一：

```text
SKILL.md
  -> SkillDefinition
  -> build_skill_descriptions 注入 system prompt
  -> retrieve_relevant_skills 注入当前请求
  -> skill 工具执行
  -> usage / feedback / evolution 审计
```

这让 Bear Code 不只是完成当前任务，还能把稳定经验变成长期能力。

## 7. 亮点六：在线 Skills 自进化

### 7.1 解决的问题

手写 Skill 很有价值，但维护成本高。用户在对话中经常给出这样的反馈：

```text
以后这类回答都要先给结论。
下次写报告要更正式，并结合政策背景。
代码审查时不要先总结，先列风险。
```

这些反馈明显具有复用价值。如果系统不能沉淀，下一次还会重复提醒。

Bear Code 的自进化链路就是从这种反馈中抽取稳定规则，并自动 add 或 merge 到 Skills。

### 7.2 对话窗口设计

Agent 每轮结束会保存 pending window：

```text
agents/agent.py:398
```

下一轮用户输入到来时会弹出上一轮窗口：

```text
agents/agent.py:376
```

这样在线沉淀看到的是：

```text
上一轮用户任务
上一轮 assistant 回复
下一轮用户反馈
检索到的 Skill reference
```

这个设计比只看单轮输入更稳，因为用户的纠错通常出现在下一轮。

### 7.3 Online Extractor

候选抽取入口：

```text
agents/online_skill_evolution.py:81
```

核心规则在 prompt 中定义：

- 用户消息是主要证据。
- Assistant 回复只是上下文。
- 下一轮用户反馈可以确认、否定或修正上一轮行为。
- 不抽取 assistant-only guesses。
- 不抽取一次性任务 payload。
- 不抽取 secrets、project facts、URLs、account IDs、exact dates、temporary parameters。
- 只抽取 durable workflow、output policy、implementation preference、correction。

这些规则在 `agents/online_skill_evolution.py:88` 到 `agents/online_skill_evolution.py:100`。

### 7.4 Online Maintainer

维护决策入口：

```text
agents/online_skill_evolution.py:136
```

Maintainer 的职责不是“抽到就写”，而是判断：

| 动作 | 说明 |
|------|------|
| `add` | 没有类似 Skill，新增 |
| `merge` | 已有类似 Skill，合并 |
| `discard` | 低价值、重复、不可复用，丢弃 |

关键代码：

- `agents/online_skill_evolution.py:146`：读取现有 Skills。
- `agents/online_skill_evolution.py:147`：exact identity 匹配。
- `agents/online_skill_evolution.py:148`：检索相似 Skill。
- `agents/online_skill_evolution.py:187`：exact match 强制 merge。
- `agents/online_skill_evolution.py:190`：如果 add 但相似度高，改成 merge。
- `agents/online_skill_evolution.py:198`：非法 action 降级为 discard。
- `agents/online_skill_evolution.py:204`：写入前确认。
- `agents/online_skill_evolution.py:218`：merge 调用 `evolve_skill()`。
- `agents/online_skill_evolution.py:230`：add 调用 `create_skill()`。

### 7.5 Online Ingest 总入口

在线沉淀总入口：

```text
agents/online_skill_evolution.py:245
```

流程：

```text
online_ingest()
  -> extract_online_skill_candidate()
  -> candidate is None: record none
  -> maintain_online_skill_candidate()
  -> record_online_provenance()
```

关键代码：

- `agents/online_skill_evolution.py:257`：调用 Extractor。
- `agents/online_skill_evolution.py:274`：没有候选时记录 `none`。
- `agents/online_skill_evolution.py:285`：调用 Maintainer。
- `agents/online_skill_evolution.py:295`：记录 provenance。

### 7.6 Skill 落盘和审计

新增 Skill：

```text
agents/skill_evolution.py:285
```

关键点：

- `agents/skill_evolution.py:305`：检查同名 Skill。
- `agents/skill_evolution.py:309`：选择用户级或项目级根目录。
- `agents/skill_evolution.py:315`：生成 frontmatter。
- `agents/skill_evolution.py:318`：初始版本 `0.1.0`。

## 8. 亮点七：Memory 与 Skills 分层

### 8.1 解决的问题

Agent 需要长期记住东西，但“记住事实”和“记住方法”不是一回事。

Bear Code 做了分层：

| 类型 | 保存内容 | 示例 |
|------|----------|------|
| Memory | 用户偏好、项目背景、历史决策、参考资料 | 用户喜欢先看结论；项目目标是做 Coding Agent |
| Skill | 可复用流程、任务方法、输出规则 | code review 先列风险；报告要正式并结合政策 |

这个分层可以避免：

- 把项目事实误沉淀成可复用方法。

## 10. 亮点九：子 Agent 和 fork-return 模式

### 10.1 解决的问题

复杂任务可能需要大量搜索和局部分析。如果全部放在主对话中，会污染上下文，也会让主 Agent 的决策负担变大。

关键代码：

### 10.4 技术亮点

子 Agent 体系把“任务拆分”和“上下文隔离”做成了统一机制：

- 只读探索不会误改文件。

- 自定义 Agent 让项目可以扩展专门角色。

## 12. 亮点十一：会话恢复与上下文压缩

### 12.1 会话恢复

会话保存由 `agents/session.py` 提供基础读写，Agent 层负责自动保存。

关键点：

- `Agent._auto_save()` 保存 metadata、Anthropic messages 或 OpenAI messages。
- `Agent.restore_session()` 恢复消息历史。
- `--resume` 通过 `get_latest_session_id()` 找最近会话。

保存路径：

```text

```

### 12.2 上下文压缩

长任务会产生大量工具结果。Bear Code 在 Agent 层做多级压缩：

| 策略 | 作用 |
|------|------|
| `_budget_tool_results_*` | token 利用率升高时截断过长工具结果 |
| `_snip_stale_results_*` | 把旧工具结果替换为占位符 |
| `_microcompact_*` | 空闲一段时间后清理旧结果 |
| `_persist_large_result()` | 超大工具结果写入 `~/.bear-code/tool-results` |
| `_compact_conversation()` | 调用模型总结历史上下文 |

其中大结果持久化在：

```text
agents/agent.py:980
```

它会把超过阈值的工具结果写入文件，只保留路径和预览，避免把上下文塞爆。

### 12.3 技术亮点

会话恢复和上下文压缩让 Bear Code 可以支撑长任务，而不是只能完成短问答：

- 退出后可以恢复最近会话。
- 工具结果不会无限堆积。
- 大输出不会直接污染上下文。
- 接近窗口限制时可以 compact。

## 15. 简历和答辩时可以强调的技术点

可以把 Bear Code 概括为：

> 基于 Python 自研轻量级 Coding Agent Runtime，统一编排 OpenAI/Anthropic 兼容模型、工具调用、权限控制、长期记忆、Skills、自进化、MCP 外部工具和子 Agent，支持会话恢复、上下文压缩和可审计的 Skill 演化链路。

可重点展开：

- **Agentic Harness**：实现模型流式调用、tool call 解析、权限检查、工具执行、tool result 回写和 session 保存。
- **自进化 Skills**：通过 pending window 捕捉下一轮用户反馈，Extractor 抽取候选，Maintainer 判断 add/merge/discard，落盘前做权限确认，演化前保存快照。
- **权限和安全**：Plan Mode 双层约束、读前编辑保护、mtime 检查、危险命令确认、settings allow/deny。
- **MCP 接入**：无 SDK 直接实现 stdio JSON-RPC，支持 initialize、tools/list、tools/call 和工具名前缀路由。
- **Memory 与 Skills 分层**：Memory 记事实，Skills 记方法，避免长期上下文污染。
- **可观察和审计**：usage、provenance、version timeline、history snapshot、skill usage stats。

## 16. 总结

Bear Code 的技术亮点不是单独某一个模块，而是多个 Agent Runtime 能力形成了完整闭环：

```text
用户任务
  -> 动态 Prompt
  -> 模型推理
  -> 工具调用
  -> 权限控制
  -> 本地执行
  -> 结果回写
  -> 会话保存
  -> Memory / Skills 长期沉淀
  -> 自进化审计
```

其中最值得深入讲的主线是：

- `agents/agent.py` 体现 Agentic Harness。
- `agents/tools.py` 体现工具和权限边界。
- `agents/skills.py`、`agents/online_skill_evolution.py`、`agents/skill_evolution.py` 体现可复用能力沉淀和自进化。
- `agents/memory.py` 体现长期记忆。
- `agents/mcp_client.py` 体现外部工具协议接入。
- `agents/subagent.py` 体现上下文隔离和任务拆分。

读懂这些代码，就能说明 Bear Code 不只是一个命令行聊天工具，而是一个具备工程闭环、权限边界、能力沉淀和扩展接口的 Coding Agent Runtime。
