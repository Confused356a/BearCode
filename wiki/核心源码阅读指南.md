# Bear Code 核心源码阅读指南

本文档面向想学习 Bear Code 源码的朋友。它不是按文件名机械罗列，而是按“读懂一个可调用工具、可沉淀 Skills、可接入 MCP 和子 Agent 的 Harness Agent”所需要的路径来组织。

建议目标：

- 第一遍读懂一次用户请求如何进入 Agent Loop。
- 第二遍读懂工具调用、权限控制、预算限制和上下文压缩。
- 第三遍读懂 Skills、Memory、MCP、子 Agent 如何接入 Runtime。
- 第四遍读懂在线 Skills 自进化和评测为什么可控、可审计。

如果你只想快速了解功能，先看 `README.md`。如果你想理解整体设计，先看 `wiki/架构设计.md`。本文档更适合一边打开源码一边阅读。

## 1. 阅读前准备

建议先把项目跑起来：

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python3 -m agents.main
```

`.env` 最小示例：

```env
APIKEY=sk-your-api-key
API=https://your-host/v1
MODEL=deepseek-chat
```

也可以使用 OpenAI-compatible 变量：

```env
OPENAI_API_KEY=sk-your-api-key
OPENAI_BASE_URL=https://your-host/v1
MODEL=gpt-4o
```

启动后可以先问：

```text
阅读 agents/main.py 和 agents/agent.py，告诉我一次请求如何进入 Agent Loop
```

常用阅读命令：

```bash
rg -n "parse_args|run_repl|run_one_shot|_resolve_api_config" agents/main.py
rg -n "class Agent|async def  chat|_chat_openai|_chat_anthropic|_execute_tool_call" agents/agent.py
rg -n "tool_definitions|get_active_tool_definitions|tool_search|check_permission|execute_tool" agents/tools.py
rg -n "discover_skills|retrieve_relevant_skills|online_ingest|format_online_skill_eval" agents
```

## 2. 总体阅读路线

![Bear Code 学习路线](assets/architecture/08-learning-roadmap.svg)

推荐阅读顺序如下：

```text
1. agents/main.py
   先看 CLI、REPL、模型配置、权限模式和预算参数怎么进入系统

2. agents/agent.py
   再看 Agent Runtime、模型循环、工具调度、会话状态和后台任务

3. agents/tools.py
   看内置工具、deferred tools、权限规则、文件读写、Shell 执行

4. agents/prompt.py
   看系统提示词如何动态拼接 Memory、Skills、子 Agent、deferred tools 和项目规则

5. agents/skills.py
   看 Skill 如何加载、检索、注入、执行和重置缓存

6. agents/online_skill_evolution.py
   看下一轮反馈如何抽取为 Skill 候选，并决定 add / merge / discard

7. agents/skill_evolution.py
   看 Skill 如何落盘、版本快照、记录 provenance、usage stats 和归档

8. agents/online_skill_eval.py
   看在线 Skill 演化如何做 lineage replay、规则评测、候选变体和 champion 记录

9. agents/memory.py
   看长期记忆如何保存、索引、召回、预取和注入

10. agents/mcp_client.py
    看 MCP Server 如何启动、发现工具和路由调用

11. agents/subagent.py
    看子 Agent 配置、发现、工具白名单和 system prompt

12. agents/session.py / agents/ui.py / agents/frontmatter.py
    最后看支撑模块
```

这条路线的思路是：先主链路，后能力模块；先运行时，后持久化；先看“怎么跑”，再看“怎么沉淀”。

## 3. 第一站：`agents/main.py`

`main.py` 是用户进入系统的地方。它的职责不是实现 Agent 能力，而是把命令行参数、环境变量和用户输入转成 Agent 可以运行的配置。

重点阅读函数：

| 函数 | 读什么 |
|------|--------|
| `parse_args()` | 支持哪些 CLI 参数，比如 `--model`、`--api-base`、`--resume`、`--plan`、`--yolo`、`--max-cost` |
| `_resolve_permission_mode()` | CLI 开关如何映射为 `default` / `plan` / `acceptEdits` / `bypassPermissions` / `dontAsk` |
| `_load_env_file()` | `.env` 是怎么被读取的 |
| `_resolve_api_config()` | 怎么判断 OpenAI-compatible 或 Anthropic-compatible |
| `run_repl()` | 交互式循环如何处理用户输入和 REPL 命令 |
| `run_one_shot()` | 一次性任务怎么调用 Agent |
| `main()` | 如何创建 Agent，并决定进入 REPL 还是 one-shot |

### 3.1 模型配置阅读重点

重点看 `main()` 中创建 `Agent` 时传入的参数：

```text
model = args.model or os.environ.get("MODEL") or "deepseek-chat"
```

模型优先级是：

```text
CLI --model
  -> .env 的 MODEL
  -> 默认 deepseek-chat
```

协议判断由 `_resolve_api_config()` 完成。你需要重点理解：

- `API` / `APIKEY` 和 `MINI_CLAUDE_API_BASE` / `MINI_CLAUDE_API_KEY` 这类通用变量怎么映射。
- `OPENAI_BASE_URL` / `OPENAI_API_KEY` 怎么使用。
- `ANTHROPIC_BASE_URL` / `ANTHROPIC_API_KEY` 怎么使用。
- base URL 包含 `/anthropic` 时为什么走 Anthropic-compatible。
- 没有 base URL 但只有通用 `APIKEY` 时，当前会回落到 Anthropic-compatible。

### 3.2 CLI 参数阅读重点

当前支持的关键参数：

| 参数 | 作用 |
|------|------|
| `--yolo` / `-y` | 使用 `bypassPermissions`，尽量跳过确认 |
| `--plan` | 使用 Plan Mode，只读探索并写计划文件 |
| `--accept-edits` | 自动批准文件编辑，但危险 shell 仍可能确认 |
| `--dont-ask` | 自动拒绝需要确认的操作，适合 CI |
| `--thinking` | 为支持的 Anthropic 模型开启 thinking |
| `--max-cost` | 设置估算成本上限 |
| `--max-turns` | 设置 agentic tool loop 最大轮次 |
| `--resume` | 恢复最近一次 session |

### 3.3 REPL 命令阅读重点

`run_repl()` 里可以看到内置命令：

- `/clear`
- `/plan`
- `/cost`
- `/compact`
- `/memory`
- `/skills`
- `/skill-stats`
- `/skill-eval`
- `/extract_now [hint]`
- `/skill-feedback <skill> <rating> [note]`
- `/skill-evolve <skill> <durable lesson>`
- `/skill-create <name> | <description> | <when-to-use> | <instructions>`
- `/<skill-name> [args]`

读这一段时要注意：REPL 命令有些直接在入口层处理，有些会调用 Agent 方法。例如 `/compact` 会走 `agent.compact()`，`/plan` 会走 `agent.toggle_plan_mode()`，`/skill-eval` 会调用 `format_online_skill_eval_async()`，`/extract_now` 会走 `agent.extract_now()`。

## 4. 第二站：`agents/agent.py`

`agent.py` 是项目最核心的文件。不要一开始从头到尾细读，否则容易陷入细节。建议按下面几个区域读。

### 4.1 先看 `Agent.__init__()`

`__init__()` 可以帮你建立 Agent 的状态模型。

重点看这些字段：

| 字段 | 含义 |
|------|------|
| `permission_mode` | 当前权限模式 |
| `thinking` / `_thinking_mode` | Anthropic thinking 是否启用，以及具体模式 |
| `model` | 当前模型名 |
| `use_openai` | 决定走 OpenAI-compatible 还是 Anthropic-compatible |
| `max_cost_usd` / `max_turns` | 成本和工具轮次预算 |
| `tools` | Agent 当前可用工具，后续可能追加 MCP 工具 |
| `_mcp_manager` / `_mcp_initialized` | MCP 管理器和懒加载状态 |
| `_anthropic_messages` / `_openai_messages` | 不同协议的消息历史 |
| `_read_file_state` | 编辑前读取和 mtime 校验 |
| `_already_surfaced_memories` / `_session_memory_bytes` | Memory 注入去重和会话注入预算 |
| `_last_retrieved_skill_reference` / `_last_retrieved_skill_hits` | 本轮检索到的 Skill 引用和命中列表 |
| `_pending_skill_extraction_window` | 等待下一轮用户反馈的 Skill 沉淀窗口 |
| `_background_skill_tasks` | 后台 Skill tracking / evolution 任务 |
| `_base_system_prompt` / `_system_prompt` | 基础提示词和运行时提示词 |

读懂这些字段后，再读后面的函数会轻松很多，因为你能知道每个函数在操作什么状态。

### 4.2 再看 `Agent.chat()`

`chat()` 是一轮用户请求的总入口。

简化流程：

```text
Agent.chat(user_message)
  -> 首次 chat 懒加载 MCP，并把 MCP 工具追加到 tools
  -> 保存原始用户输入 original_user_message
  -> 弹出上一轮 pending skill extraction window，并把本轮用户输入作为反馈补进去
  -> 检索 Skills，并把 <retrieved_skills> 注入用户消息
  -> 根据 use_openai 选择模型循环
  -> 等待模型循环结束或被 abort
  -> 收集本轮 assistant 输出
  -> 后台记录 Skill 检索使用效果
  -> 后台执行在线 Skill 自进化
  -> 设置新的 pending window
  -> 保存 session
```

这段代码非常重要，因为它把 Bear Code 的几个核心能力串起来了：

- MCP 初始化。
- Skills 检索。
- Memory 在模型循环内部异步预取。
- 模型协议路由。
- 工具调度和预算控制。
- 后台自进化。
- Session 保存。

### 4.3 看 `_chat_openai()` 和 `_chat_anthropic()`

这两个函数是两套模型协议的主循环。

阅读目标不是记住每个字段，而是理解：

- 请求模型前会准备哪些消息。
- `get_active_tool_definitions()` 如何决定模型当前能看到哪些工具。
- Memory 预取完成后如何注入最后一条用户消息。
- 模型文本如何流式打印。
- tool call 如何被解析出来。
- 权限检查在工具执行前怎么发生。
- tool result 如何回写。
- 为什么需要循环，而不是只请求一次模型。

两套循环的差异：

| 主题 | Anthropic-compatible | OpenAI-compatible |
|------|----------------------|-------------------|
| system prompt | 作为 `system` 参数传入 | 作为第一条 system message |
| 工具格式 | `input_schema` | `_to_openai_tools()` 转为 function schema |
| tool result | `user` 消息里的 `tool_result` block | `role="tool"` 消息 |
| 流式工具参数 | 通过 `partial_json` 拼接 | 通过 `delta.tool_calls` 拼接 |
| 并发优化 | 只读工具完整流出后可提前执行 | 只读工具按 batch 并发执行 |
| thinking | 支持 Anthropic thinking block | 当前 OpenAI-compatible 不处理 thinking |

理解这个差异后，你就能明白为什么 `agent.py` 要保留两套消息历史。

### 4.4 看 `_execute_tool_call()`

这是所有工具调用的统一路由入口。

重点看它如何区分：

| 工具类型 | 路由 |
|----------|------|
| Plan Mode 工具 | `_execute_plan_mode_tool()` |
| 子 Agent | `_execute_agent_tool()` |
| Skill | `_execute_skill_tool()` |
| MCP 工具 | `McpManager.call_tool()` |
| 普通内置工具 | `tools.execute_tool()` |

理解这个函数后，你会明白 Bear Code 的扩展点在哪里：新能力可以通过内置工具、Skill、MCP 或子 Agent 进入同一套 Harness。

### 4.5 看 Plan Mode

Plan Mode 涉及三处：

| 位置 | 作用 |
|------|------|
| `main.py::_resolve_permission_mode()` | `--plan` 直接进入计划模式 |
| `Agent.toggle_plan_mode()` | REPL `/plan` 手动切换 |
| `_execute_plan_mode_tool()` | 模型通过 `enter_plan_mode` / `exit_plan_mode` 切换 |

Plan Mode 的核心规则：

- 只能使用只读探索工具。
- 只能写入自动生成的 plan 文件。
- `exit_plan_mode` 后进入交互式审批流程。
- 审批后可以清空上下文再执行，也可以继续保留上下文执行，或者回到手动执行。

### 4.6 看预算、压缩和大结果持久化

长任务相关逻辑可以后看：

- `_check_budget()`
- `_auto_save()`
- `restore_session()`
- `_check_and_compact()`
- `_compact_conversation()`
- `_run_compression_pipeline()`
- `_budget_tool_results_openai()` / `_budget_tool_results_anthropic()`
- `_snip_stale_results_openai()` / `_snip_stale_results_anthropic()`
- `_microcompact_openai()` / `_microcompact_anthropic()`
- `_persist_large_result()`

这部分的目标是理解 Bear Code 如何处理长会话，而不是让每个工具结果都永久塞在上下文里。特别注意 `_persist_large_result()`：超过 30 KB 的工具结果会保存到 `~/.bear-code/tool-results/`，上下文里只保留预览和路径。

## 5. 第三站：`agents/tools.py`

`tools.py` 是内置工具、deferred tools 和权限系统。

建议先看四块：

1. `tool_definitions`
2. `get_active_tool_definitions()` / `tool_search`
3. `check_permission()`
4. `execute_tool()`

### 5.1 工具定义

`tool_definitions` 定义了模型可以调用哪些工具。你要重点看每个工具的：

- `name`
- `description`
- `input_schema`
- 是否带 `deferred`

当前内置工具：

| 工具 | 作用 |
|------|------|
| `read_file` | 读取文件，并返回带行号内容 |
| `write_file` | 写入文件，文件不存在时创建 |
| `edit_file` | 精确替换文件内容 |
| `list_files` | 按 glob 列文件 |
| `grep_search` | 搜索代码或文本 |
| `run_shell` | 执行 Shell 命令 |
| `skill` | 调用 Skill |
| `skill_create` | 手动创建 Skill |
| `skill_evolve` | 手动演化 Skill |
| `enter_plan_mode` | 进入 Plan Mode，deferred |
| `exit_plan_mode` | 退出 Plan Mode，deferred |
| `agent` | 启动子 Agent |
| `tool_search` | 搜索并激活 deferred tools |

### 5.2 Deferred Tools

当前代码不是把所有工具一次性暴露给模型。`enter_plan_mode` 和 `exit_plan_mode` 带有 `deferred=True`，默认不会出现在 active tool 列表里。

相关函数：

| 函数 | 作用 |
|------|------|
| `get_active_tool_definitions()` | 返回当前已激活的工具定义 |
| `get_deferred_tool_names()` | 给 prompt 注入 deferred 工具名称 |
| `tool_search` 分支 | 按关键词搜索 deferred 工具，并把命中的工具加入 `_activated_tools` |
| `reset_activated_tools()` | 清空已激活 deferred 工具 |

对应 prompt 在 `agents/prompt.py::build_system_prompt()` 中拼接：系统提示词会告诉模型哪些工具可以通过 `tool_search` 获取完整 schema。

### 5.3 权限系统

`check_permission()` 是重点。它会结合：

- 当前权限模式。
- 工具类型。
- 输入参数。
- `~/.bear/settings.json` 和 `<cwd>/.bear/settings.json` 里的 permission rules。
- 危险命令判断。
- 用户确认函数。

权限模式大致可以这样理解：

| 模式 | 含义 |
|------|------|
| `default` | 敏感操作需要确认 |
| `acceptEdits` | 自动接受编辑类操作，Skill 创建/演化仍可能确认 |
| `bypassPermissions` | 跳过权限确认，风险最高 |
| `dontAsk` | 自动拒绝需要确认的操作 |
| `plan` | 只允许只读探索和写计划文件 |

权限规则读取顺序是用户级再项目级，deny 先于 allow 生效。规则匹配时，`run_shell` 检查 `command`，文件类工具检查 `file_path`，并支持末尾 `*` 的前缀匹配。

### 5.4 编辑前读取保护

`write_file` 和 `edit_file` 不是直接写。它们会尽量确保：

- 文件路径可解析。
- 写入或编辑已有文件前已经读取过文件。
- 文件 mtime 没有被外部修改。
- `edit_file` 的 `old_string` 能唯一匹配。
- 返回 diff 方便审计。

这部分体现了文件编辑型 Agent 的安全边界：模型想改文件可以，但 Runtime 要确保改的是它理解过的版本。

### 5.5 搜索和 Shell

`grep_search` 会优先尝试使用 Python regex 遍历文件；`run_shell` 会通过 `subprocess.run()` 执行命令，并有 timeout。危险命令判断集中在 `is_dangerous()`，例如删除、强制操作、权限修改等命令会触发确认。

## 6. 第四站：`agents/prompt.py`

`prompt.py` 负责构建系统提示词。

重点看：

| 函数 | 作用 |
|------|------|
| `_resolve_includes()` | 处理规则文件里的 include |
| `_load_rules_dir()` | 加载规则目录 |
| `load_claude_md()` | 加载项目规则文件 |
| `get_git_context()` | 获取 Git 上下文 |
| `build_system_prompt()` | 拼接完整 system prompt |

`build_system_prompt()` 会把以下内容组合起来：

- 基础工作规则。
- 当前目录。
- 当前日期、平台、Shell。
- Git 信息。
- Memory System。
- Skills 列表。
- 子 Agent 列表。
- deferred tools 提示。
- 项目规则。

这说明 Bear Code 的 prompt 不是静态的。随着 Memory、Skills、子 Agent、deferred tools 变化，系统提示词也会变化。`Agent._refresh_runtime_system_prompt()` 会在 Skill 创建、演化或归档后刷新运行时 prompt。

## 7. 第五站：`agents/skills.py`

`skills.py` 负责 Skill 的加载、检索和执行。

重点看：

| 函数 / 类 | 作用 |
|-----------|------|
| `SkillDefinition` | Skill 在程序内的统一表示 |
| `discover_skills()` | 从用户级和项目级目录发现 Skills |
| `_load_skills_from_dir()` | 扫描目录形式的 Skill |
| `_parse_skill_file()` | 解析 `SKILL.md` frontmatter 和正文 |
| `build_skill_descriptions()` | 生成注入 system prompt 的 Skills 列表 |
| `retrieve_relevant_skills()` | 按用户输入检索相关 Skills |
| `format_retrieved_skill_context()` | 生成 `<retrieved_skills>` 注入块 |
| `execute_skill()` | 执行指定 Skill，并记录 invocation |
| `create_skill()` | 封装手动创建 Skill |
| `evolve_skill()` | 封装手动演化 Skill |
| `record_usage_judgments()` | 记录检索 Skill 是否相关、是否被使用 |

### 7.1 Skill 加载顺序

重点理解两个目录：

```text
~/.bear/skills/
.bear/skills/
```

当前实现先加载用户级 Skill，再加载项目级 Skill；项目级加载时 `overwrite=False`，所以同名时用户级 Skill 优先。

目录结构必须是：

```text
.bear/skills/<name>/SKILL.md
~/.bear/skills/<name>/SKILL.md
```

`SKILL.md` 的 frontmatter 支持：

- `name`
- `description`
- `when_to_use` 或 `when-to-use`
- `context`
- `user-invocable`
- `allowed-tools`

### 7.2 Skill 检索

`retrieve_relevant_skills()` 使用轻量 BM25 风格检索，把用户输入和 Skill 的名称、描述、`when_to_use`、正文片段做匹配。中文会拆成二元片段，英文会做基础 token 化。

它的意义是：即使用户没有手动调用 Skill，系统也能把可能相关的 Skill 上下文注入给模型。

注入格式由 `format_retrieved_skill_context()` 生成：

```text
<retrieved_skills>
...
</retrieved_skills>
```

### 7.3 Skill 执行

Skill 有两种执行模式：

| 模式 | 含义 |
|------|------|
| `inline` | 把 Skill prompt 返回给主 Agent，让主 Agent 继续执行 |
| `fork` | 创建子 Agent，以 Skill prompt 作为 system prompt 独立执行 |

对应逻辑一部分在 `skills.py::execute_skill()`，一部分在 `agent.py::_execute_skill_tool()`。

`resolve_skill_prompt()` 支持两个占位符：

| 占位符 | 含义 |
|--------|------|
| `$ARGUMENTS` / `${ARGUMENTS}` | 用户或模型传给 Skill 的参数 |
| `${CLAUDE_SKILL_DIR}` | 当前 Skill 目录，方便引用同目录的 references / scripts |

## 8. 第六站：`agents/online_skill_evolution.py`

这是在线自进化的决策层。

重点看三个函数：

| 函数 | 作用 |
|------|------|
| `extract_online_skill_candidate()` | 从上一轮任务和下一轮反馈中抽取候选 Skill |
| `maintain_online_skill_candidate()` | 判断候选应该 add、merge 还是 discard |
| `online_ingest()` | 自进化总入口 |

### 8.1 为什么要用下一轮反馈

当前轮回答结束后，Agent 并不知道用户是否认可。下一轮用户输入可能会说：

```text
刚才那个格式很好，以后都这样写
```

也可能说：

```text
刚才那种写法不行，以后不要这么写
```

所以 Bear Code 通过 pending window 把“上一轮任务 + 当前反馈”组合起来，再判断是否有可沉淀经验。

### 8.2 Extractor 和 Maintainer 的分工

Extractor 只负责判断有没有候选：

```text
上一轮用户请求
上一轮 Agent 回复
下一轮用户反馈
  -> 是否能形成可复用 Skill 候选
```

Maintainer 负责维护 Skill 集合：

```text
候选 Skill
已有 Skills
相似检索结果
上一轮 retrieved Skill reference
  -> add / merge / discard
```

`online_ingest()` 还会调用 `record_online_provenance()`，无论新增、合并、丢弃、失败还是用户拒绝，都把过程记录下来。

### 8.3 运行开关

在线演化的入口在 `Agent._run_online_skill_evolution()`。当前有两个关键环境变量：

| 变量 | 作用 |
|------|------|
| `BEAR_AUTO_SKILL_EVOLUTION` | 默认为 `1`，设为 `0` / `false` / `no` / `off` 可关闭 |
| `BEAR_AUTO_SKILL_TARGET` | 默认为 `project`，控制自动沉淀到项目级还是用户级 |

Plan Mode 下不会执行在线演化。

## 9. 第七站：`agents/skill_evolution.py`

`skill_evolution.py` 是自进化的落盘和审计层。

重点看：

| 函数 | 作用 |
|------|------|
| `get_evolution_dir()` | 获取演化数据目录 |
| `create_skill_file()` | 创建新的 Skill 文件 |
| `evolve_skill_file()` | 修改已有 Skill，并保存历史快照 |
| `record_skill_invocation()` | 记录 Skill 被调用 |
| `record_skill_feedback()` | 记录用户对 Skill 的反馈 |
| `record_online_skill_provenance()` | 记录在线沉淀来源 |
| `record_skill_usage_judgments()` | 记录 Skill 检索和使用效果 |
| `load_skill_stats()` | 读取 Skill 生命周期统计 |
| `format_skill_stats()` | 格式化输出统计 |
| `_maybe_prune_stale_skill()` | 判断长期无效 Skill 是否归档 |

这层的阅读重点是“可审计”：

- Skill 从哪里来？
- 哪次对话触发了它？
- 是新增还是合并？
- 修改前版本在哪里？
- 后续有没有被检索？
- 检索后有没有真的相关？
- 相关时有没有真的用上？
- 长期无效时是否被归档？

读完这一层，你就能解释 Bear Code 的自进化不是随意自改 prompt，而是有证据、有版本、有统计的能力沉淀。

## 10. 第八站：`agents/online_skill_eval.py`

`online_skill_eval.py` 是在线 Skill 演化的评测层，对应 REPL 命令 `/skill-eval`。

建议按下面几块读：

| 区域 | 作用 |
|------|------|
| 数据读取函数 | 读取 provenance、usage stats、active skill snapshots |
| `_build_replay_pool()` | 把在线沉淀来源整理成 replay samples |
| `_compile_eval_rules()` | 从 Skill 描述和正文编译评测规则 |
| `_summarize_rule_outcomes_async()` | 对 replay 样本执行规则评测，必要时使用 LLM judge |
| `_build_candidate_eval_bundle_async()` | 生成候选变体并在 dev/test replay 上评估 |
| `_promotion_decision()` | 判断是否更新 champion |
| `_persist_eval_artifacts()` | 保存评测产物 |
| `evaluate_online_skill_evolution_async()` | 异步评测总入口 |
| `format_online_skill_eval_async()` | 格式化 REPL 输出 |

这层回答的问题不是“要不要新增一个 Skill”，而是：

- 已经沉淀的 Skill 有没有足够 replay 样本？
- Skill 被检索后是否真的相关？
- 相关时是否真的被使用？
- 当前 Skill 版本是否通过规则评测？
- 候选变体是否优于当前版本？
- champion 是否应该更新？

它让在线自进化从“能自动写 Skill”进一步变成“能回放、能度量、能比较版本”。

| `_project_hash()` | 用当前项目路径生成隔离 hash |

Memory 和 Skills 的区别一定要记清：

## 12. 第十站：`agents/mcp_client.py`

MCP 是外部工具扩展协议。Bear Code 这里自己实现了 stdio JSON-RPC Client。

先看两个类：

| 类 | 作用 |
|----|------|
| `McpConnection` | 管理一个 MCP Server 子进程 |
| `McpManager` | 管理多个连接，合并工具定义，路由调用 |

### 12.1 `McpConnection`

重点看：

- `connect()`：启动子进程。
- `_read_loop()`：持续读取 Server 输出。
- `_send_request()`：发送 JSON-RPC 请求并等待响应。
- `initialize()`：MCP 初始化。
- `list_tools()`：列出外部工具。
- `call_tool()`：调用外部工具。
- `close()`：关闭子进程。

### 12.2 `McpManager`

重点看：

- `load_and_connect()`：读取配置并连接所有 Server。
- `get_tool_definitions()`：把 MCP 工具包装成 Agent 工具定义。
- `is_mcp_tool()`：判断工具名是不是 MCP 工具。
- `call_tool()`：根据 `mcp__server__tool` 路由到对应 Server。
- `_load_configs()`：读取全局、项目和 `.mcp.json` 配置。

配置读取顺序：

```text
~/.bear/settings.json
  -> <cwd>/.bear/settings.json
  -> <cwd>/.mcp.json
```

后读取的同名 Server 会覆盖先读取的配置。阅读目标是理解：MCP 工具最终也会进入 `Agent.tools`，并通过 `_execute_tool_call()` 统一调度。

## 13. 第十一站：`agents/subagent.py`

子 Agent 用于隔离上下文。

重点看：

| 函数 | 作用 |
|------|------|
| `_discover_custom_agents()` | 发现用户级和项目级自定义 Agent |
| `_load_agents_from_dir()` | 从目录加载 Agent 配置 |
| `get_sub_agent_config()` | 获取指定类型子 Agent 配置 |
| `get_available_agent_types()` | 列出可用子 Agent |
| `build_agent_descriptions()` | 生成注入 prompt 的子 Agent 描述 |

内置子 Agent 包括：

- `explore`
- `plan`
- `general`

自定义 Agent 目录：

```text

.bear/agents/*.md
```

这里和 Skills 的覆盖规则不同：自定义 Agent 先加载用户级，再加载项目级，项目级同名 Agent 会覆盖用户级 Agent。

真正执行子 Agent 的地方在 `agent.py::_execute_agent_tool()`。所以阅读时要把 `subagent.py` 和 `agent.py` 对照起来看。

## 17. 阅读时最容易混淆的点

### 17.1 Memory 和 Skills 不是一回事

Memory 记事实，Skills 记方法。

错误理解：

```text
只要是长期保存的东西都叫 Memory
```

正确理解：

```text
项目事实、用户偏好、历史决策 -> Memory
可复用流程、输出风格、任务方法 -> Skill
```

### 17.2 Skill 检索和 Skill 调用不是一回事

Skill 检索发生在对话前，用来给模型提示“可能相关的 Skill”。  
Skill 调用发生在对话中，是模型显式调用 `skill` 工具。

### 17.3 Skill 自动演化和手动维护不是一回事

自动演化发生在后台，由 `online_skill_evolution.py` 判断是否有可沉淀经验。  
手动维护发生在用户明确要求时，通过 `skill_create` / `skill_evolve` 工具或 REPL 的 `/skill-create` / `/skill-evolve` 命令执行。

### 17.4 MCP 工具和内置工具执行路径不同

内置工具最终进入 `tools.execute_tool()`。  
MCP 工具最终进入 `McpManager.call_tool()`。  
但它们都先经过 `Agent._execute_tool_call()`。

### 17.5 Deferred tool 和普通工具不是一回事

普通工具会直接出现在 active tool schema 里。  
Deferred tool 只在系统提示词里出现名字，模型需要先调用 `tool_search` 才能拿到完整 schema 并激活。

### 17.6 子 Agent 和主 Agent 是同一个类

子 Agent 不是另一个 Runtime。它还是 `Agent`，只是创建时设置：

```text
is_sub_agent=True
custom_system_prompt=...
custom_tools=...
```

这说明项目用同一套 Harness 支撑主 Agent 和子 Agent。

### 17.7 自进化不是立即写 Skill

当前轮完成任务后，只是保存 pending window。  
下一轮用户反馈到来后，才会判断是否抽取和沉淀 Skill。

### 17.8 用户级和项目级覆盖规则不完全一致

Skills：用户级优先，同名项目级不会覆盖用户级。  
自定义 Agent：项目级优先，同名项目级会覆盖用户级。

## 20. 最小心智模型

读完整个项目后，可以把 Bear Code 记成下面这句话：

> `main.py` 负责把用户带进系统，`agent.py` 负责 Harness 主循环，`tools.py` 执行动作并守住权限，`prompt.py` 动态拼接运行时上下文，`skills.py` 和 `memory.py` 提供长期能力与长期事实，`mcp_client.py` 和 `subagent.py` 扩展能力边界，`online_skill_evolution.py`、`skill_evolution.py` 和 `online_skill_eval.py` 把用户反馈沉淀、审计并评测成可持续演化的 Skills。

只要这个心智模型建立起来，再去读具体实现细节，就不会迷路。
