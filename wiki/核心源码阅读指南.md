# Bear Code 核心源码阅读指南

本文档面向想学习 Bear Code 源码的朋友。它不是按文件名机械罗列，而是按“读懂一个自进化 Harness Agent”所需要的路径来组织。

建议目标：

- 第一遍读懂一次用户请求如何进入 Agent Loop。
- 第二遍读懂工具调用和权限控制。
- 第三遍读懂 Skills、Memory、MCP、子 Agent 如何接入 Runtime。
- 第四遍读懂 Skills 自进化为什么可控、可审计。

如果你只想快速了解功能，先看 `README.md`。如果你想理解整体设计，先看 `wiki/架构设计.md`。本文档更适合一边打开源码一边阅读。

## 1. 阅读前准备

建议先把项目跑起来：

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python3 -m agents.main
```

`.env` 最小示例：

```env
APIKEY=sk-your-api-key
API=https://your-host/v1
MODEL=deepseek-chat
```

启动后可以先问：

```text
阅读 agents/main.py 和 agents/agent.py，告诉我一次请求如何进入 Agent Loop
```

建议准备两个终端：

- 一个终端运行 Bear Code。
- 一个终端用 `rg`、`sed`、编辑器阅读源码。

常用阅读命令：

```bash
rg -n "class Agent|async def chat|_execute_tool_call|_chat_openai|_chat_anthropic" agents/agent.py
rg -n "tool_definitions|check_permission|execute_tool" agents/tools.py
rg -n "discover_skills|retrieve_relevant_skills|online_ingest" agents
```

## 2. 总体阅读路线

![Bear Code 学习路线](assets/architecture/08-learning-roadmap.svg)

推荐阅读顺序如下：

```text
1. agents/main.py
   先看 CLI、REPL、模型配置怎么进入系统

2. agents/agent.py
   再看 Agent Runtime、模型循环、工具调度和会话状态

3. agents/tools.py
   看内置工具、权限模式、文件读写、Shell 执行

4. agents/prompt.py
   看系统提示词如何动态拼接 Memory、Skills 和子 Agent

5. agents/skills.py
   看 Skill 如何加载、检索、注入和执行

6. agents/online_skill_evolution.py
   看下一轮反馈如何抽取为 Skill 候选

7. agents/skill_evolution.py
   看 Skill 如何落盘、版本快照、记录 provenance 和 usage stats

8. agents/memory.py
   看长期记忆如何保存、索引、召回和注入

9. agents/mcp_client.py
   看 MCP Server 如何启动、发现工具和路由调用

10. agents/subagent.py
    看子 Agent 配置、发现和 system prompt

11. agents/session.py / agents/ui.py / agents/frontmatter.py
    最后看支撑模块
```

这条路线的思路是：先主链路，后能力模块；先运行时，后持久化；先看“怎么跑”，再看“怎么沉淀”。

## 3. 第一站：`agents/main.py`

`main.py` 是用户进入系统的地方。它的职责不是实现 Agent 能力，而是把命令行参数、环境变量和用户输入转成 Agent 可以运行的配置。

重点阅读函数：

| 函数 | 读什么 |
|------|--------|
| `parse_args()` | 支持哪些 CLI 参数，比如 `--model`、`--api-base`、`--resume`、`--plan` |
| `_load_env_file()` | `.env` 是怎么被读取的 |
| `_resolve_api_config()` | 怎么判断 OpenAI-compatible 或 Anthropic-compatible |
| `run_repl()` | 交互式循环如何处理用户输入 |
| `run_one_shot()` | 一次性任务怎么调用 Agent |
| `main()` | 如何创建 Agent 并决定进入 REPL 还是 one-shot |

### 3.1 模型配置阅读重点

重点看 `main()` 中创建 `Agent` 时传入的参数：

```text
model = args.model or os.environ.get("MODEL") or "deepseek-chat"
```

这说明模型优先级是：

```text
CLI --model
  -> .env 的 MODEL
  -> 默认 deepseek-chat
```

协议判断由 `_resolve_api_config()` 完成。你需要重点理解：

- `API` / `APIKEY` 这类通用变量怎么映射。
- `OPENAI_BASE_URL` / `OPENAI_API_KEY` 怎么使用。
- base URL 包含 `/anthropic` 时为什么走 Anthropic-compatible。

### 3.2 REPL 命令阅读重点

`run_repl()` 里可以看到很多内置命令，例如：

- `/help`
- `/clear`
- `/compact`
- `/cost`
- `/resume`
- `/plan`
- `/memory`
- `/skills`
- `/extract-skill`

读这一段时要注意：REPL 命令有些直接在入口层处理，有些会调用 Agent 方法。例如 `/compact` 会走 `agent.compact()`，`/plan` 会走 `agent.toggle_plan_mode()`。

## 4. 第二站：`agents/agent.py`

`agent.py` 是项目最核心的文件。不要一开始从头到尾细读，否则容易陷入细节。建议按下面几个区域读。

### 4.1 先看 `Agent.__init__()`

`__init__()` 可以帮你建立 Agent 的状态模型。

重点看这些字段：

| 字段 | 含义 |
|------|------|
| `permission_mode` | 当前权限模式 |
| `model` | 当前模型名 |
| `use_openai` | 决定走 OpenAI-compatible 还是 Anthropic-compatible |
| `tools` | Agent 当前可用工具 |
| `_mcp_manager` | MCP 管理器 |
| `_anthropic_messages` / `_openai_messages` | 不同协议的消息历史 |
| `_read_file_state` | 编辑前读取和 mtime 校验 |
| `_pending_skill_extraction_window` | 等待下一轮用户反馈的 Skill 沉淀窗口 |
| `_background_skill_tasks` | 后台 Skill tracking / evolution 任务 |
| `_system_prompt` | 当前系统提示词 |

读懂这些字段后，再读后面的函数会轻松很多，因为你能知道每个函数在操作什么状态。

### 4.2 再看 `Agent.chat()`

`chat()` 是一轮用户请求的总入口。

简化流程：

```text
Agent.chat(user_message)
  -> 首次 chat 加载 MCP
  -> 记录原始用户输入
  -> 弹出上一轮 pending skill extraction window
  -> 检索 Skills 并注入用户消息
  -> 根据 use_openai 选择模型循环
  -> 等待模型循环结束
  -> 收集 assistant 输出
  -> 后台记录 Skill 使用效果
  -> 后台执行在线 Skill 自进化
  -> 设置新的 pending window
  -> 保存 session
```

这段代码非常重要，因为它把 Bear Code 的几个核心能力串起来了：

- MCP 初始化。
- Skills 检索。
- 模型协议路由。
- 后台自进化。
- Session 保存。

### 4.3 看 `_chat_openai()` 和 `_chat_anthropic()`

这两个函数是两套模型协议的主循环。

阅读目标不是记住每个字段，而是理解：

- 请求模型前会准备哪些消息。
- 工具定义如何传给模型。
- 模型文本如何打印。
- tool call 如何被解析出来。
- tool result 如何回写。
- 为什么需要循环而不是只请求一次模型。

你可以对照看：

```text
_chat_openai()
_chat_anthropic()
```

它们的上层逻辑相似，但消息格式不同。理解这个差异后，你就能明白为什么 `agent.py` 要保留两套消息历史。

### 4.4 看 `_execute_tool_call()`

这是所有工具调用的统一路由入口。

重点看它如何区分：

| 工具类型 | 路由 |
|----------|------|
| Plan Mode 工具 | `_execute_plan_mode_tool()` |
| 子 Agent | `_execute_agent_tool()` |
| Skill | `_execute_skill_tool()` |
| MCP 工具 | `McpManager.call_tool()` |
| 普通内置工具 | `tools.execute_tool()` |

理解这个函数后，你会明白 Bear Code 的扩展点在哪里：新能力可以通过内置工具、Skill、MCP 或子 Agent 进入同一套 Harness。

### 4.5 看上下文压缩和会话

长任务相关逻辑可以后看：

- `_auto_save()`
- `restore_session()`
- `_check_and_compact()`
- `_compact_conversation()`
- `_run_compression_pipeline()`
- `_persist_large_result()`

这部分的目标是理解 Bear Code 如何处理长会话，而不是让每个工具结果都永久塞在上下文里。

## 5. 第三站：`agents/tools.py`

`tools.py` 是内置工具和权限系统。

建议先看三块：

1. `tool_definitions`
2. `check_permission()`
3. `execute_tool()`

### 5.1 工具定义

`tool_definitions` 定义了模型可以调用哪些工具。你要重点看每个工具的：

- `name`
- `description`
- `input_schema`

模型看到的是这些工具 schema，而不是 Python 函数本身。

常见工具：

| 工具 | 作用 |
|------|------|
| `read_file` | 读取文件 |
| `write_file` | 写入文件 |
| `edit_file` | 精确替换文件内容 |
| `list_files` | 列目录 |
| `grep_search` | 搜索代码 |
| `shell` | 执行 Shell 命令 |
| `skill` | 调用 Skill |
| `create_skill` | 手动创建 Skill |
| `evolve_skill` | 手动演化 Skill |
| `agent` | 启动子 Agent |

### 5.2 权限系统

`check_permission()` 是重点。它会结合：

- 当前权限模式。
- 工具类型。
- 输入参数。
- 危险命令判断。
- permission rules。
- 用户确认函数。

权限模式大致可以这样理解：

| 模式 | 含义 |
|------|------|
| `default` | 敏感操作需要确认 |
| `acceptEdits` | 自动接受编辑类操作 |
| `bypassPermissions` | 尽量跳过权限确认，风险最高 |
| `plan` | 只允许只读探索和写计划文件 |

### 5.3 编辑前读取保护

`edit_file` 不是简单字符串替换。它会尽量确保：

- 文件路径可解析。
- 替换内容能唯一匹配。
- 编辑前已经读取过文件。
- 文件 mtime 没有被外部修改。
- 返回 diff 方便审计。

这部分体现了文件编辑型 Agent 的安全边界：模型想改文件可以，但 Runtime 要确保改的是它理解过的版本。

## 6. 第四站：`agents/prompt.py`

`prompt.py` 负责构建系统提示词。

重点看：

| 函数 | 作用 |
|------|------|
| `load_claude_md()` | 加载项目规则文件 |
| `get_git_context()` | 获取 Git 上下文 |
| `build_system_prompt()` | 拼接完整 system prompt |

`build_system_prompt()` 会把以下内容组合起来：

- 基础工作规则。
- 当前目录。
- Git 信息。
- Memory System。
- Skills 列表。
- 子 Agent 列表。
- 项目规则。

这说明 Bear Code 的 prompt 不是静态的。随着 Memory、Skills、子 Agent 变化，系统提示词也会变化。

## 7. 第五站：`agents/skills.py`

`skills.py` 负责 Skill 的加载、检索和执行。

重点看：

| 函数 | 作用 |
|------|------|
| `discover_skills()` | 从用户级和项目级目录发现 Skills |
| `_parse_skill_file()` | 解析 `SKILL.md` frontmatter 和正文 |
| `build_skill_descriptions()` | 生成注入 system prompt 的 Skills 列表 |
| `retrieve_relevant_skills()` | 按用户输入检索相关 Skills |
| `format_retrieved_skill_context()` | 生成 `<retrieved_skills>` 注入块 |
| `execute_skill()` | 执行指定 Skill |
| `create_skill()` | 封装手动创建 Skill |
| `evolve_skill()` | 封装手动演化 Skill |

### 7.1 Skill 加载顺序

重点理解两个目录：

```text
.bear/skills/
~/.bear/skills/
```

项目级 Skill 适合当前项目，用户级 Skill 适合跨项目复用。阅读时要注意覆盖规则：同名 Skill 如何处理，哪个来源优先。

### 7.2 Skill 检索

`retrieve_relevant_skills()` 使用轻量检索逻辑，把用户输入和 Skill 的名称、描述、正文做匹配。

它的意义是：即使用户没有手动调用 Skill，系统也能把可能相关的 Skill 上下文注入给模型。

### 7.3 Skill 执行

Skill 有两种常见执行模式：

| 模式 | 含义 |
|------|------|
| `inline` | 把 Skill prompt 返回给主 Agent，让主 Agent 继续执行 |
| `fork` | 创建子 Agent，以 Skill prompt 作为 system prompt 独立执行 |

对应逻辑一部分在 `skills.py`，一部分在 `agent.py::_execute_skill_tool()`。

## 8. 第六站：`agents/online_skill_evolution.py`

这是在线自进化的决策层。

重点看三个函数：

| 函数 | 作用 |
|------|------|
| `extract_online_skill_candidate()` | 从上一轮任务和下一轮反馈中抽取候选 Skill |
| `maintain_online_skill_candidate()` | 判断候选应该 add、merge 还是 discard |
| `online_ingest()` | 自进化总入口 |

### 8.1 为什么要用下一轮反馈

当前轮回答结束后，Agent 并不知道用户是否认可。下一轮用户输入可能会说：

```text
刚才那个格式很好，以后都这样写
```

也可能说：

```text
刚才那种写法不行，以后不要这么写
```

所以 Bear Code 通过 pending window 把“上一轮任务 + 当前反馈”组合起来，再判断是否有可沉淀经验。

### 8.2 Extractor 和 Maintainer 的分工

Extractor 只负责判断有没有候选：

```text
上一轮用户请求
上一轮 Agent 回复
下一轮用户反馈
  -> 是否能形成可复用 Skill 候选
```

Maintainer 负责维护 Skill 集合：

```text
候选 Skill
已有 Skills
相似检索结果
上一轮 retrieved Skill reference
  -> add / merge / discard
```

这种拆分比让一个模型直接写文件更稳，因为它把“抽取经验”和“修改能力库”分开了。

## 9. 第七站：`agents/skill_evolution.py`

`skill_evolution.py` 是自进化的落盘和审计层。

重点看：

| 函数 | 作用 |
|------|------|
| `create_skill_file()` | 创建新的 Skill 文件 |
| `evolve_skill_file()` | 修改已有 Skill，并保存历史快照 |
| `record_online_skill_provenance()` | 记录在线沉淀来源 |
| `record_skill_usage_judgments()` | 记录 Skill 检索和使用效果 |
| `format_skill_stats()` | 格式化输出统计 |
| `_maybe_prune_stale_skill()` | 判断长期无效 Skill 是否归档 |

这层的阅读重点是“可审计”：

- Skill 从哪里来？
- 哪次对话触发了它？
- 是新增还是合并？
- 修改前版本在哪里？
- 后续有没有被检索？
- 检索后有没有真的用上？

读完这一层，你就能解释 Bear Code 的自进化不是随意自改 prompt，而是有证据、有版本、有统计的能力沉淀。

## 10. 第八站：`agents/memory.py`

Memory 负责长期事实和偏好。

重点看：

| 函数 / 类 | 作用 |
|-----------|------|
| `MemoryEntry` | Memory 实体 |
| `_project_hash()` | 用当前项目路径生成隔离 hash |
| `get_memory_dir()` | 获取当前项目 Memory 目录 |
| `save_memory()` | 保存 Memory |
| `list_memories()` | 列出 Memory |
| `scan_memory_headers()` | 快速扫描 Memory 元信息 |
| `select_relevant_memories()` | 用模型选择相关 Memory |
| `start_memory_prefetch()` | 异步预取 Memory |
| `format_memories_for_injection()` | 格式化为注入内容 |
| `build_memory_prompt_section()` | 构建 Memory System prompt |

Memory 和 Skills 的区别一定要记清：

| 类型 | 记什么 |
|------|--------|
| Memory | 事实、偏好、背景、决策 |
| Skills | 方法、流程、风格、操作步骤 |

如果用户说“这个项目部署在某台机器”，适合 Memory。  
如果用户说“以后写部署文档都按这个结构”，适合 Skill。

## 11. 第九站：`agents/mcp_client.py`

MCP 是外部工具扩展协议。Bear Code 这里自己实现了 stdio JSON-RPC Client。

先看两个类：

| 类 | 作用 |
|----|------|
| `McpConnection` | 管理一个 MCP Server 子进程 |
| `McpManager` | 管理多个连接，合并工具定义，路由调用 |

### 11.1 `McpConnection`

重点看：

- `connect()`：启动子进程。
- `_read_loop()`：持续读取 Server 输出。
- `_send_request()`：发送 JSON-RPC 请求并等待响应。
- `initialize()`：MCP 初始化。
- `list_tools()`：列出外部工具。
- `call_tool()`：调用外部工具。

### 11.2 `McpManager`

重点看：

- `load_and_connect()`：读取配置并连接所有 Server。
- `get_tool_definitions()`：把 MCP 工具包装成 Agent 工具定义。
- `is_mcp_tool()`：判断工具名是不是 MCP 工具。
- `call_tool()`：根据 `mcp__server__tool` 路由到对应 Server。
- `_load_configs()`：读取全局、用户、项目配置。

阅读目标是理解：MCP 工具最终也会进入 `Agent.tools`，并通过 `_execute_tool_call()` 统一调度。

## 12. 第十站：`agents/subagent.py`

子 Agent 用于隔离上下文。

重点看：

| 函数 | 作用 |
|------|------|
| `_discover_custom_agents()` | 发现用户级和项目级自定义 Agent |
| `_load_agents_from_dir()` | 从目录加载 Agent 配置 |
| `get_sub_agent_config()` | 获取指定类型子 Agent 配置 |
| `get_available_agent_types()` | 列出可用子 Agent |
| `build_agent_descriptions()` | 生成注入 prompt 的子 Agent 描述 |

内置子 Agent 通常包括：

- `explore`
- `plan`
- `general`

真正执行子 Agent 的地方在 `agent.py::_execute_agent_tool()`。所以阅读时要把 `subagent.py` 和 `agent.py` 对照起来看。

## 13. 支撑模块

### 13.1 `agents/session.py`

负责会话保存和恢复：

| 函数 | 作用 |
|------|------|
| `save_session()` | 保存 session |
| `load_session()` | 加载 session |
| `list_sessions()` | 列出历史 session |
| `get_latest_session_id()` | 找到最近 session |

Agent 层会调用这些函数实现 `--resume` 和自动保存。

### 13.2 `agents/ui.py`

负责终端输出：

- 欢迎信息。
- 用户提示符。
- Assistant 文本。
- 工具调用。
- 工具结果。
- 错误、警告、确认。
- Skills / Memory 表格。
- Plan 审批提示。

它不影响核心逻辑，但能让 CLI 体验更清晰。

### 13.3 `agents/frontmatter.py`

负责解析 `SKILL.md` 顶部 frontmatter。

Skills 需要从 Markdown 中读取：

- `name`
- `description`
- `context`
- `mode`
- `allowed-tools`

所以这里提供一个轻量解析器，避免引入复杂依赖。

## 14. 按功能反查源码

如果你不是按文件阅读，而是想理解某个功能，可以按下面的表查：

| 想理解的功能 | 先看 | 再看 |
|--------------|------|------|
| CLI 如何启动 | `agents/main.py::main()` | `run_repl()`、`run_one_shot()` |
| 模型怎么配置 | `agents/main.py::_resolve_api_config()` | `Agent.__init__()` |
| 一次请求怎么跑 | `Agent.chat()` | `_chat_openai()` / `_chat_anthropic()` |
| 工具怎么调用 | `_execute_tool_call()` | `tools.execute_tool()` |
| 权限怎么控制 | `tools.check_permission()` | `Agent._confirm_dangerous()` |
| Plan Mode 怎么实现 | `Agent.toggle_plan_mode()` | `_build_plan_mode_prompt()`、`_execute_plan_mode_tool()` |
| Skills 怎么发现 | `skills.discover_skills()` | `_load_skills_from_dir()` |
| Skills 怎么检索 | `skills.retrieve_relevant_skills()` | `format_retrieved_skill_context()` |
| Skills 怎么调用 | `Agent._execute_skill_tool()` | `skills.execute_skill()` |
| Skills 怎么自进化 | `online_ingest()` | `create_skill_file()`、`evolve_skill_file()` |
| Memory 怎么召回 | `start_memory_prefetch()` | `select_relevant_memories()` |
| MCP 怎么接入 | `McpManager.load_and_connect()` | `McpConnection.call_tool()` |
| 子 Agent 怎么跑 | `_execute_agent_tool()` | `subagent.get_sub_agent_config()` |
| 会话怎么恢复 | `session.load_session()` | `Agent.restore_session()` |
| 上下文怎么压缩 | `_check_and_compact()` | `_run_compression_pipeline()` |

## 16. 阅读时最容易混淆的点

### 16.1 Memory 和 Skills 不是一回事

Memory 记事实，Skills 记方法。

错误理解：

```text
只要是长期保存的东西都叫 Memory
```

正确理解：

```text
项目事实、用户偏好、历史决策 -> Memory
可复用流程、输出风格、任务方法 -> Skill
```

### 16.2 Skill 检索和 Skill 调用不是一回事

Skill 检索发生在对话前，用来给模型提示“可能相关的 Skill”。  
Skill 调用发生在对话中，是模型显式调用 `skill` 工具。

### 16.3 MCP 工具和内置工具执行路径不同

内置工具最终进入 `tools.execute_tool()`。  
MCP 工具最终进入 `McpManager.call_tool()`。  
但它们都先经过 `Agent._execute_tool_call()`。

### 16.4 子 Agent 和主 Agent 是同一个类

子 Agent 不是另一个 Runtime。它还是 `Agent`，只是创建时设置：

```text
is_sub_agent=True
custom_system_prompt=...
custom_tools=...
```

这说明项目用同一套 Harness 支撑主 Agent 和子 Agent。

### 16.5 自进化不是立即写 Skill

当前轮完成任务后，只是保存 pending window。  
下一轮用户反馈到来后，才会判断是否抽取和沉淀 Skill。

## 19. 最小心智模型

读完整个项目后，可以把 Bear Code 记成下面这句话：

> `main.py` 负责把用户带进系统，`agent.py` 负责 Harness 主循环，`tools.py` 执行动作并守住权限，`skills.py` 和 `memory.py` 提供长期上下文，`mcp_client.py` 和 `subagent.py` 扩展能力边界，`online_skill_evolution.py` 和 `skill_evolution.py` 把用户反馈沉淀成可审计的 Skills。

只要这个心智模型建立起来，再去读具体实现细节，就不会迷路。
